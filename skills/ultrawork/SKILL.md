# ULW scope

On explicit activation, include `ULTRAWORK MODE ENABLED!` after any host-required opening. Reading or discussing this skill does not request its execution. ULW activation persists for the session; a follow-up does not restart a workflow.

Start the input with `/ulw`, `ulw` or `ultrawork`, after optional whitespace. Specialised workflows accept their existing leading commands and aliases, such as `/ulw-plan`, `ulw plan`, `ulw-loop`, `mulw` and `meth`. A name later in the message is ordinary task text, even with a slash: `Explain /ulw`, `What does /ulw-plan do?` and `Please use ulw loop for this task` do not activate anything. Move the command or alias to the start to invoke it. Names in code, quotes, paths, relayed text and masked prohibitions remain inert.

The selected model profile owns ordinary working methods; OMP owns tool contracts, permissions, approvals and native mode capabilities. ULW adds no competing orchestration or QA procedure. The extension connects leading specialised invocations to native keywords: planning uses `ultrathink`, execution/loop uses `orchestrate`, and research/mass uses `workflowz`. A user-supplied native keyword takes precedence over that default. OMP owns the resulting notice, settings/tool gates and thinking effort; do not inject another copy or replay the trigger on follow-ups. Plain ULW selects no specialised native mode, and `jevify` remains an explicit choice.

## Goal ownership

For plain ULW, use the OMP-native goal already created by the interactive invocation route. Existing active, paused or budget-limited goals retain ownership; paused work requires explicit user direction before resuming. A recognised specialised invocation never enters the plain native-goal route, including when workflow pointers are disabled. RPC and programmatic activation alone do not create a goal; the client must use OMP's native goal API. Do not infer goal creation from this policy or create a second ULW goal, notepad or ledger for an ordinary task.

Explicit durable workflows keep their own state instead of adding a competing native goal:

- `ulw-plan`: a decision-complete plan, without product implementation.
- `ulw-execute`: a selected plan, Boulder ownership and task/evidence ledger.
- `ulw-loop`: multiple goals, dependencies and verified checkpoints.
- `mass-ulw`: a dependency graph and node recovery records; use an owning loop or execution goal when present.
- `ulw-research`: research claims, source evidence and a cited deliverable.

Read a specialised skill only when that workflow is requested or its specific artifact contract is needed. Bare ULW does not select any of them. The selected workflow owns its artifacts and continuation; the model profile supplies working methods within OMP's capability and permission contracts. Shared loop-format state does not switch standalone research into loop execution. Resume existing state rather than creating another record of the same objective. Child assignments do not inherit ULW activation or ownership of the parent workflow.

For browser work, load `skill://browser` for native Eval interaction under active host routing; static URLs use `read`. Use `skill://visual-qa/references/browser-setup.md` only for the applicable web evidence scope. Authenticated criteria require an authorized real-session relay/CDP route; managed Chromium is project-shared and does not prove signed-in behavior. Native surfaces or a legitimate selected fallback use `skill://computer-use`. Do not install/enable optional relay automatically or substitute a profile clone.

For blocked/incomplete sources, archives and platform-specific reading, load `skill://ultimate-browsing`. Delegated page work carries the browser skill's assignment contract explicitly; children do not inherit this policy or its loaded references.
